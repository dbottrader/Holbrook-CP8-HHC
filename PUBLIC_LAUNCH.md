## How to reproduce

Start with one bounded, falsifiable target rather than attempting to validate the entire ecosystem.

1. Clone the relevant repository and record the exact commit SHA.
2. Identify the exact artifact, receipt, calculation, or runtime behavior being tested.
3. Inspect its provenance record and documented verifier/test path.
4. Execute the procedure independently.
5. Record environment, dependency versions, inputs, outputs, timestamps, failures, and hashes where practical.
6. Report using:
   - **OBSERVED** — directly measured or retrieved evidence.
   - **CONTEXT** — source, chronology, environment, and boundaries.
   - **INFERENCE** — interpretation separated from observation.
   - **TEST** — evidence capable of supporting or falsifying the inference.
   - **CONCLUSION** — bounded result including uncertainty.
7. Return `PASS`, `FAIL`, or `HOLD/BLOCKED`, with unresolved gates.
8. Do not promote the claim yourself. Submit the evidence for review and Reality Veto.

A useful reproduction receipt binds, where applicable:

- repository and full commit SHA;
- artifact paths and SHA-256 values;
- deployment revision when testing a runtime;
- test command/method and execution environment;
- observed outputs and failures;
- evidence tier/disposition;
- unresolved gates;
- reviewer/agent identity without granting that identity authority.

## How to challenge a claim

A challenge is valuable when it falsifies a claim.

1. Name the exact claim.
2. Identify a discriminating test or alternative explanation.
3. Run the test without silently changing the target claim.
4. Preserve negative results and contradictions.
5. Reconcile chronology before making influence claims.
6. Do not convert structural similarity into evidence of influence or origin.

Strong challenges include counterexamples, chronology conflicts, replay failures, source/runtime mismatches, missing receipts, nondeterminism, security failures, and evidence that a planned component already exists elsewhere.

## How to contribute

High-value first contributions are concrete:

- **Reproduce:** run one bounded CP8/DAR-P test and submit the complete receipt.
- **Challenge:** select one documented claim and attempt to falsify it.
- **Audit:** bind one public deployment's observed bytes/behavior to an exact source artifact and commit—or explicitly mark it unbound.
- **Verify provenance:** independently recompute SHA-256/Merkle material for one artifact or release packet.
- **Improve:** submit a PR fixing a demonstrated defect without weakening evidence or authority boundaries.
- **Recover:** identify earlier work that supersedes proposed implementation and document `ADOPT / ADAPT / ARCHIVE / HOLD` with evidence.

Vague endorsement is not required. A failed reproduction, corrected chronology, discovered duplicate, or documented contradiction can be more valuable than agreement.
