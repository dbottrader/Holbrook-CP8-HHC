## What is ASIN-HHC / CP8?

ASIN-HHC / CP8 is an evolving research-and-builder ecosystem combining evidence-governed agent workflows, provenance/receipt infrastructure, bounded experimental runtimes, deterministic geometry and visualization labs, and human-governed promotion gates.

The project separates working implementations from experimental interpretation. Public availability is not equivalent to validation, and a deployment is not production authority.

Core governance rules include:

- Capability != Authority.
- No Receipt = No Promotion.
- Specification != Implementation.
- Registry Inclusion != Proof.
- Similarity != Influence.
- Negative evidence is first-class evidence.
- Independent branches remain isolated before synthesis.
- Reality Veto remains human/physical-world authority.
- ADOPT / ADAPT before BUILD.

Evidence claims should be normalized as **OBSERVED / CONTEXT / INFERENCE / TEST / CONCLUSION**.

## What is experimental?

The following remain explicitly bounded and must not be inferred as promoted merely because artifacts or demos exist:

- geometry/glyph interpretations that lack independent reproduction;
- origin hypotheses derived from crop-circle, glyph or related pattern investigations;
- autonomous agent-mesh authority beyond evidenced runtime behavior;
- HHC-SIM as anything other than simulation;
- monetary/token authority;
- production cryptography claims for historical/raw prototype paths;
- independent witness/reproduction claims without receipts;
- any promotion above the evidence level actually earned by reproducible tests.

## How to reproduce

A useful reproduction does not begin by agreeing with the project. It begins by trying to reproduce or falsify a bounded claim.

1. Select one artifact, runtime behavior, calculation, geometry output, receipt or governance decision.
2. Record the exact source commit/file and any deployment URL used.
3. State the claim using OBSERVED / CONTEXT / INFERENCE / TEST / CONCLUSION.
4. Run the test independently where possible. Preserve environment, inputs, outputs and timestamps.
5. Hash resulting artifacts/receipts with SHA-256.
6. Report failures, contradictions and negative results rather than suppressing them.
7. Do not convert a successful local reproduction into a broader production or origin claim.

A reproduction earns authority only for what was actually reproduced.

## How to contribute

Concrete contribution lanes:

### Reproduce

Re-run an existing CP8 test or deterministic artifact and submit the environment, inputs, outputs and receipt.

### Challenge

Select a documented claim and attempt to falsify it. Alternative explanations and failed reproductions are valuable contributions.

### Audit

Audit one bounded surface for source/runtime drift, security assumptions, nondeterminism, provenance gaps or unsupported language.

### Bind provenance

Take an existing deployment/artifact and establish source commit -> artifact bytes -> deployed bytes where technically possible.

### Build a missing edge

Only after checking existing artifacts, implement a genuinely missing integration edge. Prefer ADOPT or ADAPT over recreating an existing subsystem.
